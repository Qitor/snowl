# 01: Current Architecture Analysis

## 1.1 Data Flow

```
project.yml
  -> ProjectConfig (provider, model matrix, code paths, runtime)
  -> load_project_components() (dynamic import of task.py, agent.py, scorer.py)
  -> PlanBuilder.build() (Task x AgentVariant x Sample -> PlanTrial[])
  -> RuntimePolicy.resolve() (budgets from config + heuristics)
  -> ResourceScheduler (semaphores for trial/scoring/container/provider)
  -> Eval loop (asyncio task dispatch with FIRST_COMPLETED)
    -> EvalTrialLifecycle.run()
      -> prepare_trial_phase() (validate, resolve tools, sandbox/container prep)
      -> execute_agent_phase() (agent.run(state, context, tools))
      -> score_trial_phase() (scorer.score via asyncio.to_thread)
      -> finalize_trial_phase() (teardown sandbox/container)
  -> Artifacts (manifest, plan, events, outcomes, aggregate)
```

## 1.2 Core Contracts

### Task (`snowl/core/task.py`)
```python
Task(task_id, env_spec, sample_iter_factory, metadata)
TaskProvider: list_splits(), count(), iter_tasks(), get_task()
```
- **Issue**: `sample_iter_factory` is a callable, not an async iterable, preventing lazy streaming of large benchmark datasets.

### Agent (`snowl/core/agent.py`)
```python
Agent: agent_id, async run(state: AgentState, context, tools) -> AgentState
AgentState: messages, actions, observations, output, stop_reason
StopReason: COMPLETED | MAX_STEPS | LIMIT_EXCEEDED | ERROR | CANCELLED
```
- **Strength**: Clean async protocol, well-defined state machine.
- **Issue**: No built-in concept of "emulated tool execution" - the agent always receives real or stub tools. ToolEmu needs an LM emulator sitting between agent tool calls and observations.

### Scorer (`snowl/core/scorer.py`)
```python
Scorer: scorer_id, score(task_result, trace, context) -> dict[str, Score]
Score(value, explanation, metadata)
```
- **Critical Issue**: `score()` is synchronous. In `score_trial_phase()` it runs via `asyncio.to_thread()`. This means:
  1. Scorer cannot make async model API calls (e.g., LLM-as-judge)
  2. Scorer cannot participate in provider admission for judge models
  3. Blocking I/O in scorers wastes scoring slots

### TaskResult (`snowl/core/task_result.py`)
```python
TaskResult(task_id, agent_id, sample_id, seed, status, final_output, timing, usage, error, artifacts, payload)
TaskStatus: SUCCESS | INCORRECT | LIMIT_EXCEEDED | ERROR | CANCELLED
```
- **Issue**: `payload` is an opaque dict used as a catch-all for benchmark-specific data. No schema enforcement.

### EnvSpec (`snowl/core/env.py`)
```python
EnvSpec(env_type, provided_ops, sandbox_spec, config)
SandboxSpec(provider, config, spec_hash())
```
- **Issue**: No concept of "emulated environment" where tool results are generated by an LM rather than real execution.

### ToolSpec (`snowl/core/tool.py`)
```python
ToolSpec(name, description, parameters, callable, required_ops)
@tool decorator, ToolRegistry
```
- **Issue**: Tool `callable` is sync. No async tool execution protocol. For ToolEmu's adversarial emulator, we need a tool wrapper that calls an LM to generate observations.

## 1.3 Concurrency Model

### ResourceScheduler (`snowl/runtime/resource_scheduler.py`)
Five independent semaphore-based budgets:

| Budget | Semaphore | Purpose |
|--------|-----------|---------|
| `max_running_trials` | asyncio.Semaphore | Concurrent agent execution phases |
| `max_container_slots` | asyncio.Semaphore | Container/sandbox admission |
| `max_scoring_tasks` | asyncio.Semaphore | Concurrent scoring |
| `max_builds` | threading.BoundedSemaphore | Image/container builds |
| `provider_budgets[id]` | asyncio.Semaphore | Per-provider model API calls |

**Eval loop dispatch** (in `snowl/eval.py`):
```python
max_inflight = max_running_trials + max_scoring_tasks
# asyncio.create_task for each trial
# asyncio.wait(inflight, return_when=FIRST_COMPLETED)
```

**Provider enforcement**: `OpenAICompatibleChatClient.generate()` acquires provider admission at HTTP call level via global slot resolver.

### Problems with Current Concurrency

1. **No sample-level parallelism**: Each `(task, agent, sample)` is a separate trial. For ToolEmu's 144 cases across 3 agent types, that's 432 trials dispatched one at a time. The framework can't parallelize tool calls within a single agent run.

2. **Scorer blocks scoring slot**: `asyncio.to_thread(scorer.score)` occupies a scoring slot for the duration, even if the scorer is making HTTP calls to a judge model. The scoring slot semaphore doesn't interact with provider admission.

3. **Docker-like heuristic is too coarse**: `is_docker_like_task()` forces `max_running_trials=1` for all Docker/container tasks, even when multiple containers could run concurrently with proper resource isolation.

4. **No backpressure from provider to scheduler**: If all provider slots are occupied, new trials still enter the prepare phase, wasting container/workspace resources.

5. **No batch-level parallelism**: ToolEmu's `FuncExecutorWithRetry` uses batch processing (batch_size=5-10) with `ThreadPoolExecutor` for parallel generation within a batch. Snowl has no equivalent concept.

## 1.4 Benchmark Adapter Architecture

### BaseBenchmarkAdapter (`snowl/benchmarks/base_adapter.py`)
Template method pattern:
```python
class BaseBenchmarkAdapter(ABC, Generic[RowT]):
    _iter_rows() -> list[RowT]          # Load all data eagerly
    _row_split(row, row_index) -> str   # Assign split
    _row_to_sample(row, ...) -> dict    # Map to {id, input, metadata}
    _env_spec() -> EnvSpec              # Environment requirements
    _matches_filters(row, filters) -> bool
    load_tasks(split, limit, filters) -> list[Task]  # Orchestrates above
```

**Problems**:
1. **Eager data loading**: `_iter_rows()` returns a full list. For large benchmarks, this forces all data into memory at once.
2. **No runtime integration**: The adapter only maps data to samples. It cannot configure:
   - How tools should be executed (real vs. emulated)
   - What scorer concurrency profile to use
   - Whether to use benchmark-specific agent scaffolding
3. **Single Task per load**: `load_tasks()` always returns `[task]` (a single task containing all samples). This prevents split-level parallelism.

### Benchmark Registry (`snowl/benchmarks/registry.py`)
```python
BenchmarkInfo(name, domain, benchmark_type, family, primary_metric, ...)
```
- Registry is metadata-only; no runtime behavior is attached.
- No way to register benchmark-specific runtime policies, scorer factories, or tool providers.

## 1.5 Scorer Library

### Agent-Oriented Scorers (`snowl/scorer/agent.py`)
Rich set of composable primitives:
- `ToolTracePolicyScorer`: Check forbidden/required tools, argument patterns
- `StateTransitionScorer`: Check pre/post state transitions
- `CheckpointScoreScorer`: Weighted composite of named checkpoints
- `CanaryLeakScorer`: Detect canary leakage
- `WorkspaceDiffScorer`: Check file system changes
- `FunctionCallMatchScorer`: Exact function call matching

### Composition Problems
1. **Ad-hoc composition**: `AgentDojoScorer` manually calls three sub-scorers and wires their outputs together via `TaskResult(payload={"checkpoints": ...})`. This is fragile and non-declarative.
2. **No async scoring**: All scorers are sync, preventing LLM-as-judge from being first-class.
3. **No metric aggregation**: Scorers produce per-sample `Score` values but there's no framework-level aggregation (accuracy, stderr, grouped metrics). The `aggregate_outcomes` function in `snowl/aggregator.py` works at the trial outcome level, not the metric level.

## 1.6 Summary of Architectural Issues

| # | Issue | Impact | Affected Benchmarks |
|---|-------|--------|-------------------|
| A1 | Sync scorer protocol | Blocks scoring slots, can't use judge models natively | ToolEmu (needs LM evaluation), all future LLM-judge benchmarks |
| A2 | No sample-level parallelism | Large benchmarks serialize at trial level | ToolEmu (144 cases), AgentDojo (97+ tasks) |
| A3 | No emulated environment abstraction | Can't run ToolEmu's LM-emulated sandbox | ToolEmu |
| A4 | Eager data loading | Memory pressure for large datasets | All benchmarks |
| A5 | No benchmark-specific runtime profiles | Suboptimal concurrency defaults | All benchmarks |
| A6 | Ad-hoc scorer composition | Fragile, non-reusable wiring | AgentDojo, ToolEmu |
| A7 | No deferred scoring | Can't rescore with different scorers | All benchmarks |
| A8 | No metric aggregation framework | No accuracy/stderr/grouped stats | All benchmarks |
| A9 | No async tool execution | Can't emulate tools with LM calls | ToolEmu |
| A10 | Provider backpressure gap | Wasted resources when API-congested | All benchmarks |
